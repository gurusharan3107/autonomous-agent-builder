Automation · Mental model · For cutting hands-on toil

When to use what — so the machine maintains itself

Four automation surfaces, one decision. Git hooks, GitHub Actions, GitHub webhooks, and Claude Managed Agents are not competing tools — they are four rungs of one ladder. Learn the ladder and the manual-maintenance part of your week shrinks toward zero.

The trick isn't picking one. It's pushing every task down to the cheapest rung that can do it — and letting the expensive rungs fire automatically so you're never the trigger.

The one mental model

Every surface is just a point on four axes

Stop memorising features. Any automation surface is fully described by four questions. Answer them for your task and the right tool falls out — that's the whole skill.

AXIS 1

Where does it run?

The machine that executes the work. Determines what it can touch and whether it needs setup.

your laptop → GitHub runner → your server → Anthropic cloud
AXIS 2

What triggers it?

The event that wakes it. The closer to "the moment work happens", the tighter the feedback loop.

git commit → PR / cron → any repo event → API call
AXIS 3

Deterministic or judgment?

The decider. A fixed rule (lint passes / fails) needs no model. A call that varies needs one.

fixed rule (free) → a model decides (tokens)
AXIS 4

What does it cost?

Time + money + a thing you now own. Cheapest-that-works wins; every automation is also maintenance.

milliseconds → cloud minutes → model tokens
The four rungs

Each surface, by its sweet spot

Read each card as: where it runs · what fires it · the one job it's best at · what it costs you. The "reach for it when" line is the trigger to memorise.

Rung 1 · local fence

Git hooks

Runs
Your machine, before code enters git history
Fires on
git commit / git push
Decider
Deterministic — no model
Cost
Milliseconds to seconds · free
Reach for it when a fast, fixed check must block bad code before it ever exists: format, lint, test-sync, secret-scan.
⚠ Bypassable with --no-verify and only on your machine — always mirror the same check in Actions so it's actually enforced.
Rung 2 · cloud backbone

GitHub Actions / workflows

Runs
GitHub cloud runners, clean each time
Fires on
push · PR · cron · issue/PR events · manual · webhook
Decider
Usually deterministic; can call a model
Cost
Minutes · runner time
Reach for it when work needs a clean environment, must run regardless of local discipline, or should happen on a schedule: full test suite, build/deploy, nightly sweeps. Also the orchestrator that triggers the rung above.
⚠ "Workflows" and "Actions" are the same thing — the YAML in .github/workflows/ configures Actions runs.
The wiring

GitHub webhooks

Runs
Nothing — delivers an event to your endpoint
Fires on
Any GitHub event, in real time
Decider
N/A — pure transport
Cost
An endpoint you must host + secure
Reach for it when a GitHub event must reach a long-running external service (a Managed Agent, a bot, Slack) that Actions can't reach, or you need real-time push instead of a polling job.
⚠ Lowest-level rung. If an Action can already do the job, you don't need a webhook.
Rung 3 · autonomous worker

Claude Managed Agents

Runs
Anthropic cloud — sessions, memory, sandbox
Fires on
API call · webhook · schedule
Decider
A model — judgment is the point
Cost
Model tokens + an integration to build
Reach for it when work is long-running, async, stateful, and judgment-heavy and shouldn't hold a terminal: triage a queue, investigate over many runs, draft autonomous fix-PRs.
⚠ Beta (header required), not ZDR/HIPAA-eligible, rate-limited (~300/600 RPM), and can't touch your local files — it works through git/GitHub. Earns its keep at queue/team scale, not solo housekeeping.
The rule that ties it together

Push down. Trigger up.

Push every task to the cheapest rung that can do it — deterministic work belongs in hooks and Actions, never a model. Then trigger the expensive rungs automatically — a scheduled Action or a webhook wakes the agent, so you are never the trigger. Manual maintenance is just work that hasn't been pushed down or wired up yet.

deterministic → hook / Action needs a model → Claude, fired by an Action long & async at volume → Managed Agent event → external agent → webhook

Honest caveats — read before you build

What bites people

  • Don't build the cloud-agent pipeline before you have the volume. For a solo dev / single repo, Actions + the Claude GitHub integration covers ~80%. Managed Agents pay off at queue / team / product scale — a backlog, long async jobs — not one repo's chores.
  • Every automation is a thing you now maintain. Question the chore before automating it: a flaky, low-value gate should be deleted, not wrapped in YAML. Automate the frequent, deterministic, genuinely-yours tasks; cut the rest.
  • Match the model tier even inside CI. A scheduled triage/label job that calls a model should call a cheap one; reserve the frontier model for the investigate/fix-PR jobs. Same "cheapest that works" rule, applied to automation.
  • Hooks are a fence, not a wall. --no-verify walks right past them and they only run on your machine. The real enforcement is the mirrored check in Actions.
  • Webhooks are infrastructure. An endpoint to host, a secret to verify, retries to handle. Don't reach for one when a scheduled Action polling the API would do.
