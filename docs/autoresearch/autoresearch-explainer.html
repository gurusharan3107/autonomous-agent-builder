How autoresearch works in autonomous-agent-builder

TL;DR — Autoresearch is an autonomous optimization loop (inspired by Karpathy's autoresearch methodology) that improves the Builder's prompt/context assembly through systematic code-generation testing. Each iteration makes a bounded source edit, runs 5 scripted fixtures against a live Builder workspace, measures noncached_plus_output_tokens, and keeps or discards the change based on a 2σ noise floor. The core philosophy: rapid autonomous iteration at small scale beats big runs at slow cadence.

When to reach for autoresearch — and when not to

Autoresearch is for one job: changing prompt/context assembly and proving the change is real before keeping it. Everything else is the wrong tool.

Use it when

  • You suspect the Builder is wasting tokens on prompt/context assembly
  • You have a bounded source edit to test (single file, single behavioural change)
  • You want a 2σ-significance verdict, not a feel-good before/after vibe
  • The change is measurable in noncached_plus_output_tokens on at least one fixture
  • You already have a stable baseline — or you're willing to run one ($5–10, ~2 h)
  • You're prepared to discard the edit if the loop says DISCARD, no matter how clean it looked in dev

Don't reach for it when

  • You're shipping a user feature — wrong lane, use the Builder dashboard
  • The change isn't visible in billed tokens (UX polish, validation logic, error messages)
  • You have no clean baseline and don't have ~2 h + $5–10 to establish one
  • You want to refactor — the loop demands one behavioural change at a time
  • The change spans multiple files in non-prompt code paths
  • You're debugging — use builder logs analyze, not the optimization loop
★
Mental model. Autoresearch is a microscope, not a hammer. It exists to detect signal smaller than the noise floor of one-off runs. If the change you're testing is obvious — saves 50% of tokens, breaks a gate, etc. — you don't need autoresearch. If the change might save 5–15% and you can't tell whether it's real, you do.

The five-step loop

Each iteration of the Iterate lane is one trip around these five steps. Expand each to see what runs and where. The whole loop takes 10–30 minutes per iteration depending on the fixture.

1 Make a bounded source edit operator-edit

The loop pauses for the operator to edit exactly one of six allowed files in the prompt/context assembly path. The edit must be bounded — a single behavioural change, not a refactor — so any composite-metric delta is attributable. v1 cannot edit code itself; this is the only step that requires a human.

2 Run a fixture against a live Builder workspace scripts/autoresearch/run.py

Copies the immutable seed (~/.seed/devpulse) to a fresh worktree, starts a Builder process, drives one scripted fixture prompt (A–E) over the HTTP API, waits for shipped or a 1500 s timeout, then runs npm build and the test suite. Telemetry is captured per-session.

3 Measure billed tokens via session telemetry builder logs analyze --session

The composite metric is noncached_plus_output_tokens — non-cached input plus output. Cached reads are free and excluded. This is the single optimization target. A prior multi-dimensional formula was retired in P16 (CV = 77.5% → 14.7% on single dimension).

4 2σ comparison vs baseline scripts/autoresearch/compare.py

The candidate must beat μ − 2σ of the baseline distribution to be statistically significant. compare.py also evaluates the six hard gates. Any single gate failure flips the verdict to DISCARD regardless of composite delta.

5 Keep, discard, or fix scripts/autoresearch/loop.py

KEEP → promote fixture A's win to fixtures B–E for confirmation. DISCARD → revert the source edit, mark the idea attempted. CRASH → bail to the Fix lane to patch the harness or seed. State is persisted to docs/autoresearch/PROGRESS.md.

The three lanes

Every autoresearch session enters one lane. The skill asks via AskUserQuestion at /start unless the operator names a lane explicitly.

Establish the noise floor

Duration · ~2 h Cost · $5–10 N · 5 fixtures × 5 runs = 25

Required before any iteration. Without σ you can't tell signal from noise.

  1. Preflight (recipe 1) — 8 hard + 5 soft checks for $0
  2. baseline.py --fixtures A,B,C,D,E --n 5
  3. Per-fixture μ, σ, and 2σ-floor written to baseline_runs_summary.json
  4. Each fixture marked stable only when ≥ 3 clean runs land
  5. Closeout: render_iterations.py + freshness_sweep.py + PROGRESS.md entry
# Required entry command
python scripts/autoresearch/baseline.py \
  --fixtures A,B,C,D,E --n 5 --output docs/autoresearch/

Pick an idea, edit, verdict

Duration · 10–30 min / iter Prerequisite · Baseline stable Lane · Karpathy loop

The hot loop. Top unattempted idea from OPTIMIZE_IDEAS.md, operator makes the source edit, fixture A runs, 2σ verdict decides.

  1. loop.py picks the top unattempted idea
  2. Loop pauses for the operator's bounded edit
  3. run.py executes fixture A end-to-end
  4. compare.py emits KEEP / DISCARD / CRASH
  5. KEEP → promote A's win to B–E. DISCARD → revert & mark attempted
# Entry — picks the top idea automatically
python scripts/autoresearch/loop.py --fixture A

# Or target a specific idea
python scripts/autoresearch/loop.py --idea 4 --fixture A

Patch a defect the loop surfaced

Trigger · Loop can't patch itself Examples · contract violation, schema drift, telemetry gap

The escape hatch when the loop hits a measurement defect or harness-contract violation it can't auto-heal. Patches go to source, not to the loop.

  1. Identify the gap from compare.py CRASH evidence
  2. Confirm self_heal.py can't address it (5 known patterns only)
  3. Source patch + test + re-snapshot seed if needed
  4. Re-baseline the affected fixtures before resuming Iterate
  5. Closeout: PROGRESS.md entry tagged fix

The six hard gates

Each run must pass all six. A single failure flips compare.py to DISCARD regardless of composite delta. No "almost passed" — the gates exist precisely to refuse runs that look cheap but ship something broken.

GatePass conditionWhy
cache_ratio> 5×Caching is working; non-cached tokens reflect real new work.
chunk_pressure_riskfalseNo context-pressure signals — the assembly is healthy.
avoidable_cost_flags[ ]No telemetry-flagged waste (Builder's own optimization hints).
gate_pass_rate= 1.0Every Builder phase-gate passed (planning, design, quality, etc.).
feature_correcttrueThe fixture's feature acceptance check passed.
full_shiptrueBuilder reached shipped status — not incomplete, crash, or timeout.

What it can and cannot do

Can

  • Measure composite metric repeatably across 5 fixtures
  • Run N = 5 baseline to establish σ-floor
  • Auto-heal 5 catalogued failure patterns deterministically
  • Session-scoped telemetry (post M2.3 fix)
  • Per-agent token attribution
  • Enforce lane structure with mandatory preflight + freshness sweep
  • Apply six hard gates on every run

Cannot (yet)

  • Edit source code itself — v1 pauses for operator
  • Run full ship-cycle validation automatically
  • Merge approved optimizations autonomously
  • Per-message granularity telemetry
  • Path B (source-level context attribution)
  • Handle unknown error signatures — escalates to human
  • Recover from tracked-file changes / git pollution without re-snapshot

FAQ

Why noncached_plus_output_tokens instead of a richer composite?
The earlier composite (token × operator_turns × wallclock_s) had a coefficient of variation of 77.5% — too noisy to detect real improvements. The single-dimension billed-token metric dropped CV to 14.7% (P16). Lower is better; cached reads are free and excluded because they don't bill.
Why a 2σ floor specifically?
A 1σ improvement happens by chance ~16% of the time on a normal distribution; 2σ ~2.3%. With 11 ideas in the backlog, a 1σ bar would accept noise as signal multiple times before the season is out. 2σ is the cheapest defensible bar.
Why does v1 pause for the operator's edit?
Because the measurement infrastructure must be more reliable than the thing being measured. The loop establishes that the measurement is trustworthy first (baseline + gates + self-heal). Autonomous source edits come after the loop has proven it can detect real change without human review.
What happens if a fixture's σ is unreliable?
The fixture is marked unstable in baseline_runs_summary.json and excluded from comparisons until it has ≥ 3 clean runs. As of this writing fixtures A and B are stable; C–E need more runs before broad iteration.
How does self-heal differ from the Fix lane?
self_heal.py patches 5 catalogued patterns deterministically with no LLM calls (1 fix + 1 retry cap). Everything else escalates to the Fix lane — a human-driven source patch path, typically against the harness, the seed, or telemetry, not the Builder itself.
