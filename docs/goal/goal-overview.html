02North Star

The mission and the definition of "preferred" · NORTH-STAR.md

Make Autonomous Agent Builder the preferred app for taking software from idea to shipped — over Codex CLI and Claude Code — for both non-technical operators and experienced developers. One chat-first, dashboard-backed operating environment that runs identically on the Claude Agent SDK or the Codex SDK.

Not a model-provider wrapper. The operating environment for agent-era software delivery.

Three bars for "preferred" — all must hold

Bar 1 — Operator UX win

Idea → shipped feature with zero exposure to lifecycle / sprint / task / worktree / gate / MCP / SDK. Builder asks only product questions.

Tier 1
Bar 2 — Developer economics win

Same feature ships with fewer tokens, turns, wall-clock and approvals — plus stronger durable state. cache_ratio>5x, chunk_pressure_risk:false.

Tier 1 + Tier 3
Bar 3 — Lifecycle completeness win

Only tool covering requirements → design → backlog → implementation → verification → ship → optimize as one resumable loop.

Tier 2

Differentiators no plain agent CLI matches

Chat-only surface, real dashboardNo flags, no model picker. Status and approvals live in product surfaces.
Durable lifecycle stateBacklog, sprints, approvals, recovery persist across sessions, lanes, restarts.
Builder-owned agent intelligenceModel, effort, allowlist, prompt, context are product policy — operator says what, Builder decides how.
Native two-lane runtimeFirst-class Claude + Codex SDK with identical product behavior.
Memory & knowledge as system jobsDurable lessons accumulate automatically; future sessions inherit precedent.
Cost-aware executionTokens, cache ratios, chunk pressure are first-class dashboard evidence.
Voice as a peer surfaceRealtime voice (Samantha) shares state and approval flow with chat.
Resumability after dropA fresh agent pointed at docs/goal/ continues from STATUS.md alone.
Executable governance via skillsAudit, optimization, continuity disciplines run as project-local skills.

Non-goals

  • Thin wrapper over Codex CLI / Claude Code with a UI.
  • Manual orchestration where the user picks model / tools / context.
  • Doc store with no execution.
  • "Power-user" tool requiring internals knowledge.
  • Single-runtime product (Claude-only or Codex-only).

Design principles (always-on)

  • Chat-first for the user; structured execution underneath.
  • Durable state over ephemeral agent behavior.
  • Retrieval before guesswork.
  • System-owned workflow decisions over user micromanagement.
  • Root causes over symptom patches — SDK-grounded, never workarounds.

05Hard Rules

Non-negotiable, every session · README.md

  1. STATUS.md must not lie. Update on every transition. Wrong STATUS = Tier 1 resumability failure.
  2. Everything maps to ROADMAP. No ad-hoc work; new work lands in the right epoch first.
  3. EVALUATION is the bar. Done only when the claimed tier passes with evidence.
  4. INDEX is the owner map. One owner per concern; check before creating/editing any doc.
  5. Both lanes first-class. Claims must hold in claude and codex_sdk.
  6. Operator-language mandatory on operator surfaces.
  7. The model owns prompt interpretation. Deterministic routing on exact wording is a hard violation.
  8. Fix root causes per the Fix Standard. SDK-grounded, no workarounds.
  9. Inspect neighbouring surfaces when testing. One-surface verification is unverified.
  10. Memory is bidirectional. Read precedent before fixing; write durable learnings back.
  11. Autoresearch (Track B) is activating. Don't run it on broken behavior.
  12. A [x] isn't closed until pushed.
  13. Commit only on [x] close — CHANGELOG → tick → STATUS → one commit → push.

06Fix Standard — the Seven Steps

Doctrine for every non-trivial fix; ordered · FIX-STANDARD.md

  1. Load repo precedent. builder memory search from the source repo — 90+ memories encode prior decisions.
  2. Explore the codebase. Find the real owning module; don't guess by filename.
  3. Load required triggers. Quality gate + workflow summary before touching CLAUDE.md / AGENTS.md / runtime / CLI.
  4. Ground the fix in SDK docs. Cite the SDK feature — no workarounds. Needs something the SDK lacks → wrong layer.
  5. Apply at the correct layer. Orchestrator → route → runtime adapter → frontend. Don't patch UI if the backend is wrong.
  6. Verify with gates + a regression test that fails without the fix and passes with it. The test is the durable artifact.
  7. Write memory back if durable. Owner boundaries, recurring traps, SDK gotchas. Invalidate stale memory.

Forbidden: symptom-level patches, workarounds in lieu of SDK grounding, bypassing visible surfaces (raw API/DB/CLI writes), generated-app hand-patches.

08Tuning & Autoresearch

Two cadences for "less spend per shipped feature" · TUNING.md

Manual tuning (this folder)

  • Interactive, within a test cycle; tester judgment.
  • Continuous CLI monitoring during a run (board / logs analyze / errors).
  • Per-prompt loop: enumerate tool calls → is each in the agent's job? → remove or delegate → re-run.
  • Output: tool-allowlist + boundary changes.

Autoresearch (Track B)

  • Autonomous, measured, continuous.
  • Hard-gate + 2σ composite test from a baseline variance floor.
  • Three lanes: Baseline → Iterate → Fix.
  • Output: prompt-shape + context-block changes; feeds Tier-3 evidence.
