architecture & lifecycle reference
post M1.4

You describe what to build.
An AI team plans it, codes it, tests it, and ships it.

Autonomous Agent Builder is a structured software development platform. You are the Operator — you add features to a backlog, start a sprint, and approve key decisions. A team of specialized AI agents does the rest: planning architecture, writing code in an isolated workspace, running quality checks, and opening a pull request with evidence. Every step is visible on the dashboard, and nothing is committed without your sign-off at the gates that matter.

Three Roles in Every Sprint
Operator
You
You own the product vision. You add features to the backlog, launch sprints, and approve design decisions and quality gate findings. The dashboard is your control surface — the agents work for you, not the other way around.
Orchestrator
The State Machine
A deterministic phase router. It reads TaskStatus from the database, dispatches the correct agent for each phase, handles retries and blocked states, and advances the task. It never improvises — every decision is encoded in phase handlers.
Agents
The Builders
Thirteen specialized AI agents — each owns one phase. They execute inside isolated workspace directories, use builder tools (read, edit, run tests, search KB), and produce structured evidence that lives in the database. No agent has access to another agent's state.

A Task is the smallest execution unit — one isolated workspace directory, one agent run per phase. The orchestrator reads TaskStatus and routes the task through all phases until it reaches DONE. Sessions are persisted: if a task resumes after a rate-limit or approval, the same workspace directory and session ID are reused exactly.

A sprint is a partnership. You make the decisions that need a human — what to build, whether the design is right, whether a quality failure should block the PR. Everything else is handled automatically, in order, without you having to manage the sequence.
1
Set up the project
You do
Run builder init in your app workspace. Choose a runtime — Claude Agent SDK or Codex SDK. Complete the Day-0 readiness checklist (git, auth, workspace path).
Happens automatically
Builder creates the runtime contract file — CLAUDE.md for Claude lane, AGENTS.md for Codex lane. Day-0 gate is computed and stored. No agents can run until the gate passes.
Settings → Runtime · builder readiness status
2
Describe what you want built
You do
Add a feature to the backlog on the Backlog page. Write a description, acceptance criteria, or have a conversation with the init-project-chat agent (opus model) to work through requirements interactively.
Happens automatically
The feature is stored with a unique ID. At sprint time, the planner agent breaks it into tasks with acceptance criteria and a dependency graph.
Backlog → New Item
3
Start a sprint
You do
Move backlog items into a sprint on the Board. Click Start Sprint (or the equivalent CLI command). That is the last action you take for a while.
Happens automatically
The orchestrator picks up tasks in PENDING state, advances them to PLANNING, and dispatches the planner agent. If sprint-level plan/design artifacts already exist, covered tasks skip separate planning runs.
Board → Sprint Planning
4
Watch agents work
You do
Open the Agent Page and watch. You can observe every tool call, file edit, and line of reasoning in real time. You don't need to do anything until an approval gate appears.
Happens automatically
Orchestrator runs each phase in order: planner (architecture) → designer (ADRs + API contracts) → code-gen (writes code in isolated workspace, 30 turns). Both runtimes stream output to the same dashboard.
Agent Page → Live Transcript
5
Approve the design (and any gate failures)
You do
After the designer agent finishes, the task pauses at DESIGN_REVIEW. You review the architecture decision records and API contracts on the Approvals page. Approve to proceed; reject with feedback to re-run the designer.
Happens automatically
If quality gates fail after implementation, the gate-remediator agent (sonnet, 16 turns) attempts auto-fix — lint errors, type annotations, import issues. Only if remediation fails after retries does it reach you as a blocked gate.
Approvals → Review & Approve
6
PR is created — merge when ready
You do
Review the pull request on GitHub. The PR description includes structured evidence: lint results, test output, security scan summary, and diff. Merge when satisfied. The task stays at REVIEW_PENDING until you act.
Happens automatically
Before creating the PR, the documentation-bridge validates that the knowledge base is fresh — delegating to a documentation-agent subagent if any docs are stale. The pr-creator agent then bundles all evidence and opens the PR.
Agent Page → PR Link
7
Task is Done — the system learns
You do
Nothing. The task reaches DONE automatically after the build-verifier confirms the post-merge build is green.
Happens automatically
The optimization-agent reviews observability data, telemetry, and builder recommendations. It updates the generated-app runtime guidance (CLAUDE.md / AGENTS.md) and deterministic scripts to make future runs faster and more reliable.
Metrics → Observability
Provider Limit Handling
If an agent hits a rate or usage limit mid-run, the task transitions to CAPABILITY_LIMIT — not FAILED. The reset metadata is stored (code, reason, reset time, hint). When the provider resets, the orchestrator resumes the same task at the same phase automatically. No manual database repair, no lost progress.

Quality Gate — Auto-Remediation Loop (M1.4)
What happens when quality gates fail at QUALITY_GATES phase:
6 Gates Run → FAIL remediation_possible? → YES gate-remediator agent → Gates Re-run → PASS → PR_CREATION
The gate-remediator is a targeted, scope-limited agent (sonnet, max_turns=16). It can fix: lint errors, type annotation issues, import resolution, and configuration problems. It is explicitly prohibited from deleting files, changing business logic, or modifying API contracts. If remediation fails after retries, the task moves to BLOCKED and an approval gate appears for you.
Off-Path States — Phase Is Never Lost
BLOCKED
Waiting on an operator decision or missing prerequisite. Current phase is preserved. Resume from the Approvals page or after resolving the blocker.
CAPABILITY_LIMIT
Provider hit a rate or usage limit. Reset metadata is stored (time, hint, source). Orchestrator auto-resumes when the provider window resets — no manual action needed.
FAILED
Unrecoverable error. Root cause stored in AgentRun.error. View on the Observability page. Create an incident item in the backlog for follow-up.
DESIGN_REVIEW
Special approval state — awaits your sign-off after the designer agent completes. Can be skipped if sprint-level plan/design artifacts already cover the task.

The architecture is layered by who can see it. The top layer is runtime-agnostic — backlog, approvals, quality gates, the database, and the dashboard work identically regardless of which AI runtime you choose. Below that, the orchestrator manages phase routing. Below that, two parallel runtime lanes (Claude SDK and Codex SDK) both normalize their output into the same RunResult structure that feeds the convergence layer.

Each agent owns exactly one phase. They do not communicate with each other — they read inputs from the database and workspace, write evidence back, and return. The orchestrator decides what runs next. Model selection is policy, not user choice — execution_policy.py resolves the right model for each agent type and phase.
Orchestrator-Dispatched Agents — the main pipeline
AgentPhaseModelTurnsWhat it does
planner PLANNING opus 20 Reads the feature description and sprint context. Produces a structured task tree — subtasks, dependencies, acceptance criteria, complexity estimate. Sprint-level plans can cover multiple tasks (covered tasks skip separate planning runs).
designer DESIGN opus 20 Produces architecture decision records (ADRs), API contracts, data model changes, and interface specifications. Searches the knowledge base for existing patterns and memory for prior decisions before proposing anything new.
scaffold IMPLEMENTATION sonnet 12 Sets up workspace structure, generates boilerplate, and prepares the environment before the main code-gen run. Runs before code-gen when scaffolding is needed.
code-gen IMPLEMENTATION sonnet 30 The primary build agent. Reads design artifacts and acceptance criteria, writes code in the isolated workspace, runs tests incrementally using mcp__workspace tools. Session is persisted — if the task resumes after a rate-limit or BLOCKED state, the same workspace and session ID are reused.
gate-remediator QUALITY_GATES sonnet 16 Targeted quality-gate error fixer. Fixes lint errors, type annotations, import issues, and configuration errors. Explicitly prohibited from deleting files or changing business logic. Fires only when remediation_possible=True is returned by a failing gate.
integration-resolver INTEGRATION sonnet 20 Resolves git rebase conflicts before PR creation when the workspace branch has diverged from the target branch.
pr-creator PR_CREATION sonnet 15 Creates a pull request with structured evidence — lint results, test output, security scan, diff summary. Only used for real Git workspaces with a PR target. For Codex workspaces without a Git PR target, change_evidence and build_verify deterministic scripts cover this instead.
build-verifier BUILD_VERIFY sonnet 10 Post-merge build confirmation. Runs the full test suite, checks integration tests, verifies no regressions. Produces structured pass/fail evidence stored in the AgentRun record.
feature-verifier VERIFICATION sonnet 24 Validates features against acceptance criteria. Generates and runs Playwright tests for browser-visible proof when needed.
documentation-bridge PR_CREATION sonnet 8 Validates KB freshness before PR creation. If any docs are stale, delegates to the documentation-agent subagent to refresh them. Re-validates before allowing PR creation to proceed.
optimization-agent DONE sonnet 14 Post-ship optimization. Reviews observability recommendations, preflight evidence, telemetry, and logs. Updates generated-app CLAUDE.md / AGENTS.md runtime guidance and project-local deterministic scripts. Any script it creates records which phase should use it and what evidence it replaces.

Specialist Subagents — Evidence Lanes (Claude SDK only)
Subagents are bounded evidence lanes. They return structured JSON to the parent agent run. They do not own lifecycle state, approvals, backlog, or board — they exist purely to provide evidence. Each runs with its own model, tool set, and turn budget.
SubagentModelEvidence Produced
repo-researcher haiku Read-only repository structure, ownership mapping, and codebase analysis. Used by planner and designer for context gathering.
browser-verifier haiku Browser-visible acceptance evidence via Playwright. UI regression summaries and screenshot proof.
build-verifier (subagent) haiku Deterministic build/lint/test proof. Returns structured pass/fail evidence with full command output.
security-reviewer sonnet Security and permission-risk analysis on code changes. Returns structured vulnerability findings.
pr-reviewer haiku PR-readiness evidence and risk summaries. Reviews diff, tests, and docs before pr-creator fires.
documentation-agent sonnet KB maintenance — updates feature docs, testing guides, and API references. Invoked by the documentation-bridge parent agent.
Model Policy — M1.4
Model, effort, subagent, and context strategy are builder-owned runtime policy in execution_policy.py. The operator never selects Haiku/Sonnet/Opus manually — the policy resolves the correct model for each agent type and phase. Per-phase tool allowlists (M1.4) control which tools each agent can call within each phase, enforced at PreToolUse. Preflight probes validate workspace readiness before each agent dispatch.
Two execution engines, one product. You can switch between them in Dashboard Settings — everything else (backlog, approvals, quality gates, dashboard) stays identical. Claude SDK gives you hooks, subagents, MCP, and per-phase model policy. Codex SDK gives you native sandbox isolation, real-time token streaming, and subscription auth.
