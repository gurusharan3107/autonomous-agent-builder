Executive summary

Every gate's control surface was extracted (commands, expectations, owned files), verified against the live CLI and filesystem, then scored 0–10 for scope clarity, overlap, and enforcement strength. The surfaces are well-scoped and almost entirely wired correctly — but one structural fact dominates everything below.

The framework finding — gates are retrieval, not enforcement

builder quality-gate <surface> is a retrieval surface that always returns status: ok. It emits the doc's commands + expectations; it never computes pass/fail. So ~73% of all expectations are agent-self-judged prose with no executable backing. Only 3 of 17 gates pull most of their expectations through to a real test/script/lint. This is by design, but it means gate "passing" mostly measures whether an agent read and reasoned, not whether the property holds.

Concrete defects to fix

All verified this run. Ordered by severity. None block the merge you just did — these are pre-existing.

  1. codex-subagents is degraded (5/10). Three real problems: (a) workflow summary codex-routing-policy errors despite appearing in the hint list; (b) workflow summary codex-project-productivity-setup is a dead doc ref; (c) its deterministic check scripts/check_codex_subagents.py returns ok:false in a clean checkout because .codex/config.toml is gitignored, and the gate's own Pass Criteria require architecture_reviewer.toml which is absent from .codex/agents/ (only code-reviewer + code-simplifier present). The gate contradicts itself.
  2. Dead MISSION.md reference in two gates. agent-quality and documentation-agent both list workflow --docs-dir docs read MISSION.md in their commands[] — it fails at runtime, and both doc bodies already struck it through (~~MISSION.md~~). Front-matter is stale relative to the body. Remove the command + related_doc entry in both.
  3. generated-app-acceptance lists prose as a command. "Use Chrome plugin against the generated app localhost URL" sits in the structured commands[] array but is a manual instruction, not a resolvable command. Move it to the body.
  4. Three gates declare no related_docs. approval, verification, and quality-gates have no front-matter owner links (verification compensates with valid inline body refs; approval has none). Add owner links for navigability.
  5. claude-md's central criterion is unfalsifiable. It demands "concise" with no line/byte threshold while the file it governs is ~197 lines / 1.9k words. Either set a measurable budget or reword the expectation.
  6. quality-gates hosts an un-governed taxonomy. Its 4 front-matter expectations cover task-surface rendering only, but the body carries a repo-wide validation-routing taxonomy that no expectation governs and no check validates.

What's healthy

Worth stating plainly so the defects above stay in proportion:

  • Scope clarity is near-universal. 16 of 17 gates have an unambiguous "When To Load" trigger list. Only the diffuse Claude-SDK-tuning overlap muddies which gate owns a given lever.
  • Wiring is almost clean. Across ~90 commands and all declared owner files, only 5 references are dead/mis-typed — and 3 of those are the same MISSION.md / codex-doc rot, not 5 independent rots.
  • The 4 most consequential gates are the best-enforced (verification, knowledge-base, complexity, modular-runtime) — the places where "passing" must mean something mechanical actually do.
